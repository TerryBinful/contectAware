# Document 04 — Dataset & Research-Question Feasibility Assessment

**Date:** 17 September 2026
**Status:** Independent audit document; extends (does not repeat) the Stage 1 audit using external evidence. Does not constitute the final research paper.

## Purpose

To determine, using externally verified dataset documentation and the design specified in Document 03, whether the ExtraSensory dataset and the existing project experimental design can actually support the three research questions in the reformulated pivot — RQ1 (score validity), RQ2 (decision-layer mechanism comparison), RQ3 (robustness/context-dependence) — and the more granular RQ1–RQ4/H1–H4 already specified in `01_preregistration_template.md`. This is not assumed; it is assessed against confirmed dataset statistics.

## Evidence-provenance note

As in Document 01, the "Stage 1 audit" facts asserted in the task brief (one-vs-rest model, random row-level 80/20 split, SMOTE, reproducible Gradient Boosting result, 597→49 transition reduction) could not be located as an uploaded artifact in this project. ## Evidence

### A. Confirmed dataset facts [External, verified]

From the [official ExtraSensory dataset site](http://extrasensory.ucsd.edu/) and [Vaizman, Ellis & Lanckriet (2017), *IEEE Pervasive Computing* 16(4):62–74](http://extrasensory.ucsd.edu/papers/vaizman2017a_pervasiveAcceptedVersion.pdf):

| Fact | Value |
|---|---|
| Number of users | 60 (34F/26M, average age 25) |
| Total labeled examples | 308,320 (labeled), representing 308,320 minutes |
| Labeled examples per user | Range 685–9,706; mean 5,139 (SD 2,332) |
| Additional unlabeled examples per user | Range 2–6,218; mean 1,150 (SD 1,246) |
| Days of participation per user | Range 2.9–28.1 days; mean 7.6 days (SD 3.2) |
| Recording schedule | App automatically records a **20-second sensing window approximately once per minute**; examples are **not guaranteed to be continuous** — time gaps occur |
| Devices/wearables | 34 iPhone, 26 Android users; 56 of 60 wore a Pebble smartwatch |
| Average labels applied per example | 3.8 (SD 1.4); range 1.1–9.7 |
| Sensor coverage (labeled examples) | Accelerometer 308,306; Gyroscope 291,883; Location 273,737; Watch accelerometer 210,716 — i.e. **not every sensor is present for every example**, and coverage varies by modality |

**Critical correction carried forward from earlier project work (now independently reconfirmed):** the 20-second figure is the **recording-window duration inside each minute**, not the inter-example interval. The nominal cadence between examples is ~60 seconds, and even that is not guaranteed — gaps occur. Any claim describing the decision cadence as "20 seconds" is not supported by the dataset documentation and must not be used.

### B. ANGA/ANIA metric provenance re-check [External, verified — partial correction to project knowledge wiki]

The project knowledge wiki attributes ANGA/ANIA to "Bours et al. 2015." Independent search initially located secondary citations abbreviating the source as "[BM15b]" and inferred an author order of "Mondal & Bours"; on closer verification against the primary record this was wrong and is corrected here. The actual paper is **Bours, P. & Mondal, S. (2015), "Performance evaluation of continuous authentication systems," *IET Biometrics*, 4(4), 220–226, DOI: 10.1049/iet-bmt.2014.0070** — confirmed directly via the [IET Digital Library record](https://digital-library.theiet.org/doi/abs/10.1049/iet-bmt.2014.0070), independently corroborated by an [Oxford thesis citation](https://ora.ox.ac.uk/objects/uuid:077d9dcc-83e5-484b-a4ba-4d8fa14ea385/files/m2eaf5b87657133ae2e8cb15979971860) ("Patrick Bours and Soumik Mondal. 'Performance evaluation of continuous authentication systems'. In: IET Biometrics 4.4 (Dec. 2015), pp. 220–226") and an [Oxford asiaccs17 paper's reference list](https://www.cs.ox.ac.uk/files/14899/asiaccs17.pdf) ("P. Bours and S. Mondal. Performance evaluation of continuous authentication systems. IET Biometrics, 4(4):220–226, 2015"). Author order is **Bours first, Mondal second** — the reverse of my initial secondary-source inference — and there is a single 2015 paper, not a "(2015b)" variant; no second 2015 ANGA/ANIA-defining paper was located. The project knowledge wiki's existing "Bours et al. 2015" attribution is therefore substantively correct on venue and year; the only refinement needed is naming both authors explicitly (Bours & Mondal) rather than using "et al." for a two-author paper. The project's own pre-existing `06_literature_to_add.md` file already names this paper correctly (title and venue match exactly), which this document did not check before an earlier, now-corrected draft of this section — a caution for future single-pass verification.

**More important structural correction:** the original ANGA/ANIA metrics, as described by every secondary source found, are defined as the average number of genuine **actions** (e.g., keystrokes) before a false lock, and average number of impostor **actions** before detection — an **action-count** metric, appropriate for discrete-event modalities like keystroke dynamics. The project's own scaffolding files (`02_splice_benchmark_spec.md`, `03_mechanism_reference.md`) define **ANGA-time** and **ANIA-time** — a **time-normalized** adaptation ("genuine minutes / false locks," "minutes from switch to detection"). This is a sensible and necessary adaptation for a continuous sensor stream, which has no natural discrete "action" unit the way keystrokes do — but it must be explicitly presented in the thesis as **the project's own adaptation of Bours & Mondal's (2015) original action-count metric to a time-normalized form**, not as a direct reproduction of the original metric. Conflating the two would misattribute a specific methodological choice to a source that did not make it.

### C. Feasibility of the splice benchmark given confirmed dataset volume

`02_splice_benchmark_spec.md` [Project, Level 1] requires, per genuine user and per condition (X, M): ≥10 sequences, with impostor block lengths L ∈ {3, 10, 30, 60} minutes drawn from **contiguous** impostor test-period runs (gaps ≤ 2·Δt), and genuine flanks of at least W = ⌈5 min/Δt⌉ frames on each side of the splice.

Given the confirmed per-user statistics:

- **Mean labeled examples per user: 5,139**, over a mean participation window of **7.6 days**. At a nominal ~1-minute cadence this is consistent with the reported example count (7.6 days × 1,440 min/day ≈ 10,944 possible minutes; 5,139 labeled + 1,150 unlabeled ≈ 6,289 actual examples out of ≈10,944 possible slots ≈ 57% coverage) — confirming substantial, expected gaps in the recording stream, consistent with the "do not splice across recording gaps" safeguard already built into the spec.
- **Chronological 60/20/20 split** (per `01_preregistration_template.md`) leaves a **test-period** stream of only ~20% of each user's data — for the mean user, roughly 1,000–1,200 labeled examples spanning roughly 1.5 days of calendar time, but with the same ~57% gap rate, so the number of genuine **contiguous** runs long enough to serve as flanks (≥5 minutes each side) is a nontrivial constraint, not a given.
- **Users at the low end of the range (685 labeled examples total, or the low end of the 7.6±3.2-day participation range)** will have a test-period stream of well under 200 labeled examples — almost certainly too sparse and gap-prone to reliably supply ≥10 valid splice sequences with 60-minute contiguous impostor blocks in condition M (context-matched), which additionally requires a matching dominant-activity label. `02_splice_benchmark_spec.md` already anticipates this with its "skip and log" rule and "coverage" reporting — this is the correct mitigation, but the **magnitude** of expected exclusion has not yet been quantified against the actual per-user distribution, and should be computed empirically (a direct, mechanical audit of the real per-user gap structure) before the splice benchmark is finalized, not assumed adequate from the aggregate statistics alone.
- **Recommendation:** run the coverage/exclusion audit specified in `02_splice_benchmark_spec.md` §9 (sanity checks) explicitly as its own first output, and report — before any mechanism results — the fraction of the 60 users retained after applying the ≥10-sequences-per-condition requirement, especially at L=60 minutes and condition M. If a substantial fraction of users must be excluded, this directly affects the statistical power of the Wilcoxon/Friedman procedures validated in Document 03, since their unit of analysis is the retained user, not the full 60.

### D. RQ1 feasibility — score validity

RQ1 (as reformulated) concerns whether the upstream authentication score itself is valid (subject-independent, not leaking, not a trivial shortcut) before any decision-layer mechanism is layered on top. `01_preregistration_template.md` §4 already specifies subject-disjoint impostor training/test partitioning and per-fold-only preprocessing (median imputation, RF feature selection, SMOTE — all fitted inside the training fold only). This is externally supported as the leakage-safe order by [Demircioğlu (2024)](https://www.nature.com/articles/s41598-024-62585-z) (Document 03, Evidence E). **Feasibility verdict: supported**, contingent on the design actually being implemented as specified (this document cannot confirm implementation, only design adequacy — see Section E below on the Stage-1-reported claims).

One additional dataset-level risk for RQ1: location and phone-state features are known, easily-learned proxies for identity/context in ExtraSensory (a concern already flagged in the project's prior work per the task brief's "location-derived performance" caution). The confirmed sensor-coverage table above shows location is present for only 273,737 of 308,320 labeled examples (≈89%) — meaning a location-dependent model would need explicit handling of missing-location frames, which is a concrete, checkable implementation requirement for RQ1's "no feature-shortcut" condition, not yet confirmed as implemented anywhere in the accessible project repository.

### E. RQ2 feasibility — decision-layer mechanism comparison

This is the RQ most directly supported by the design validated in Document 03: fixed score generator, matched-operating-point comparison across mechanisms defined identically in `03_mechanism_reference.md`, primary Wilcoxon + recommended Friedman/Nemenyi secondary analysis. **Feasibility verdict: supported**, contingent on the splice-benchmark coverage risk in Section C being adequately resolved (i.e., enough users retain enough valid sequences per condition to give the statistical tests adequate power).

### F. RQ3 feasibility — robustness / context-dependence

RQ3 (robustness/context-dependence), as reformulated, actually spans two of `01_preregistration_template.md`'s more granular questions, and both must be addressed for RQ3 to be considered fully covered: (i) RQ3 ("Is any hysteresis advantage attributable to the joint effect of margin and dwell, rather than either component alone?"), tested by Exp 3 (hysteresis component ablation, HIGH VALUE in `04_experiment_plan.md`, answering H3) — this arm's feasibility depends only on the Exp 2 mechanism bake-off data already being collected, not on label coverage, so it is **supported** independent of the audits below; and (ii) RQ4 ("Do findings differ between cross-context X and context-matched M impostors?"), tested by Exp 4 (feature-group ablation, marked OPTIONAL in `04_experiment_plan.md`). The context-matched condition M construction is confirmed as project-original design (Document 03, Evidence C) with no located external precedent — this is not a defect, but it means RQ3's validity rests entirely on the internal coherence of the dominant-activity-label matching procedure (`CONTEXT_LABELS` list in `02_splice_benchmark_spec.md`), which itself depends on ExtraSensory's label sparsity. Confirmed dataset statistics show an average of only 3.8 applied labels per example (SD 1.4, range 1.1–9.7) out of the full label taxonomy — meaning many examples will lack any of the 11 `CONTEXT_LABELS` used for matching, directly feeding into the "if no match exists... skip and log it" rule and the coverage-reporting requirement already specified. **Feasibility verdict: conditionally supported** — the mechanism for testing RQ3 is well-designed, but its statistical power depends on the empirically unconfirmed match-coverage rate under real label sparsity, which should be measured directly (per the same audit recommended in Section C) before RQ3 is treated as adequately powered.

### G. Status of the Stage-1-reported claims specifically

The task brief instructs treating the following as established project evidence: 60 participants, contextual/device-motion features including location and device-state variables, one-vs-rest model construction, random row-level 80/20 split, SMOTE, a reproducible Gradient Boosting result, replay through instantaneous-threshold and hysteresis rules, and a 597→49 transition reduction on one target participant's stream.

- The **60-participant** and **location/device-state feature** claims are consistent with, and now independently confirmed by, the external ExtraSensory documentation (Section A) — this much can be treated as externally corroborated even without the missing audit document.
- The **one-vs-rest construction, random row-level 80/20 split, SMOTE application, Gradient Boosting result, and 597→49 transition figure** are **specific implementation and results claims that this document cannot verify**, because no code, notebook, log, or the referenced audit document exists in the accessible project repository. They are recorded here as **[Stage-1, reported]** per the evidence hierarchy, not as confirmed findings.
- **Methodological implication if taken at face value:** a "random row-level 80/20 split" (as distinct from the chronological, subject-disjoint split specified in `01_preregistration_template.md`) would very likely mix temporally adjacent frames between train and test — a form of temporal leakage independent of, and in addition to, any SMOTE-related concern. This is consistent with the methodological issues the task brief itself lists as already identified (temporal leakage) and is now further supported by the general external evidence on cross-validation design (Demšar 2006's emphasis on independence between units; Demircioğlu 2024's preprocessing-order finding) — but the row-level-split claim itself remains unverified as an actual implementation fact, only plausible as described.
- **The 597→49 transition reduction, even if accurate as a raw count**, cannot be treated as a security result — this is consistent with, and independently reinforced by, the score/decision distinction maintained throughout Documents 01–03: a reduction in transitions on a single stream, replayed rather than evaluated on the open-set splice-benchmark design specified in `02_splice_benchmark_spec.md`, measures stability of that one stream only, not detection latency, false-lock rate, or any matched-operating-point security property.

## Analysis: feasibility matrix

| RQ | Data adequate? | Method adequate (per Doc 03)? | Key unresolved risk | Verdict |
|---|---|---|---|---|
| RQ1 (score validity) | Yes, with the caveat that ~11% of examples lack location data and must be handled explicitly | Yes, subject-disjoint + fold-only preprocessing already specified | Confirm the *new* pipeline (not the Stage-1-reported one) is what will actually be implemented | Conditionally supported |
| RQ2 (decision-layer comparison) | Yes, contingent on splice-benchmark coverage audit | Yes — most fully validated design of the three RQs (Document 03) | Empirical per-user sequence-coverage rate not yet measured | Conditionally supported, pending coverage audit |
| RQ3 (robustness/context-dependence) | Marginal — label sparsity (3.8 labels/example average) constrains context-matching coverage | Yes, mechanism well-specified | Match-coverage rate under real label sparsity not yet measured | Conditionally supported, pending coverage audit |

No RQ is rated "unsupported" outright; none is rated fully, unconditionally "supported" either, because two shared empirical prerequisites (per-user splice-sequence coverage; context-label match coverage) have well-specified audit procedures already sitting in the project's own files but have not yet been run against the actual data.

## Conclusions

**Evidence:** ExtraSensory's confirmed per-user data volume (mean 5,139 labeled examples over a mean 7.6-day window, with roughly 57% slot-fill rate) is adequate in aggregate for the reformulated pivot's three research questions, but the *specific* splice-benchmark and context-matching designs both depend on per-user contiguous-run availability and label-coverage rates that have not yet been empirically measured against the real dataset, despite the relevant audit procedures already existing in the project's own scaffolding files.

**Interpretation:** The dataset is very likely capable of supporting RQ1 and RQ2 with the current design. RQ3 is the most exposed to the label-sparsity risk and should be treated as the most conditional of the three until the match-coverage audit is run. None of this depends on the missing "Stage 1 audit" — this feasibility assessment stands on the confirmed dataset documentation and the project's own already-specified (and externally well-supported) experimental design.

**Recommendation:** Run the per-user coverage/exclusion audit (splice-sequence availability by condition and L; context-label match rate) as the immediate next practical step, before any mechanism results are produced — this is cheap, mechanical, and directly resolves the only two conditional items in the feasibility matrix. Correct the ANGA/ANIA attribution in the project knowledge wiki and in any future writing from "Bours et al. 2015" to the fully named **"Bours & Mondal (2015)"** (venue/year were already correct; only the "et al." shorthand needed expanding to both named authors), and explicitly label the time-normalized ANGA-time/ANIA-time variants as the project's own adaptation. Do not treat the Stage-1-reported 597→49 result, or its described row-level split, as verified evidence in any downstream document; if the underlying code/notebook exists outside this project, uploading it would allow direct verification instead of continued reliance on the user-reported description.
